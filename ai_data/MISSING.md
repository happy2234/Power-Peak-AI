# Missing, not feasible, or different from the request

- Feature groups: the requested split (weather 35, calendar 26, lag 12, rolling 9, other 13) is NOT what `src/walkthrough.feature_group` gives (31/25/9/3/27). It is reproduced exactly by `ai_group()` in the script: Lag = `*lag*` and `*_last`; Rolling = `*roll*`, `*_std7`, `*_std30`; Weather = weather variables plus `d_*` weather deltas and `wx_source`; Calendar = calendar/festival/holiday features incl. `ref_holidays`; Other = the rest (target `_r` and `_mask` inputs, `h`, `h_frac`, `is_imputed`, `ref_imputed`, `ref_tmax_ai`, `ref_cdd_ai`, `ref_app_tmax_ai`). So 'no weather' still keeps the three `ref_*` weather reference levels; an extra row `no_weather_incl_ref_levels (extra)` removes them too.
- Ablation uses the fixed split (fit origins to 2024-12, validation Jan-Mar 2025, test from 2025-04-01) and `models/lgbm/best_params_fixed_split.yaml`, not the production hyper-parameters (the production model is trained on all data, so it has no held-out test). Validation MAPE is optimistic: the validation slice drives early stopping and the conformal term. `weather_only` / `calendar_only` also remove `h` (it is in group Other).
- The all-features ablation fit reproduces the stored fixed-split LightGBM test MAPE to within 0.04 pp (3.34/2.30/2.81 vs 3.31/2.27/2.77 for solar/evening/energy): the stored fit is not byte-reproducible from the current feature build (the weather archive has grown since). Test origins are cut at 2026-11-07 to match the stored split.
- Validation set for LSTM permutation importance and TFT variable-selection/attention: the last 15 % of origins (the model's own validation definition). The shipped models were re-fitted on train+validation afterwards, so this slice is not unseen data; read the importances as 'what the model relies on', not as out-of-sample skill.
- LightGBM validation loss per iteration is not stored by the project; `lightgbm_training_curve.csv` is recomputed in memory on the fixed split (not the production model).
- Training time: for LSTM/TFT `training_seconds` in model_cards = sum of per-epoch seconds in history.csv (main loop only); `extra.training_log_seconds_incl_refit` has the training_log.jsonl figure. LightGBM time is from training_log.jsonl.
- Trained-model parameter counts for LSTM/TFT come from instantiating the stored networks; LightGBM 'parameters' = total trees (sum of the 9 boosters).
- metrics_by_horizon.csv excludes Grid-India: its `h` counts days from its forecast-week start, not from an issue date.
- predictions_long.csv holds the 6 headline models only (not the 13 other backtest variants). Grid-India has no P10/P90.
- Fixed-test-split bias % and Grid-India rows are computed here from fixed_split_predictions.parquet and the Grid-India rows of backtest_processed.parquet (date >= 2025-04-01; Grid-India days start 2025-05-01 in the backtest file).
- worst_days.csv / errors_by_group.csv: a target day's error is the mean over its available days-ahead forecasts. Weather condition and tmax_ai quartiles use OBSERVED weather (evaluation labels only).
- worked_example: lag/rolling values are computed for forecast origin 2026-11-14 (the example day as the last observed day); LSTM scaled values are the last encoder day (2026-11-14) and the 7 decoder days after it. A forecast issued on 2026-11-14 and the latest stored forecast (origin 2026-11-21) are both included; `actual` is in the value column where known.
- fixed_split_predictions.parquet is not in this project; read from /home/gauravkumar/projects/india-power-forecast (its fixed_split_tables.parquet and fixed_split_info.json are identical to this project's; MAPEs reproduce fixed_split_tables.parquet exactly).
- model_ladder.csv: the requested order is NOT monotone: TFT is worse than the previous step (+0.24 pp); Grid-India is worse than the previous step (+1.83 pp)
